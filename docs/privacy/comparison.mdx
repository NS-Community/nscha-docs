# 与常见方案对照

下表右列描述的是**一类托管式验证方案的常见做法**，不指向任何具体产品。对照的目的是说明取舍，不是评价优劣。

| 维度 | NSCHA | 常见托管式验证 |
| --- | --- | --- |
| 请求目的地 | <span className="nscha-yes">仅本站源</span> | 第三方服务域名 |
| Cookie / 本地存储 | <span className="nscha-yes">不写入</span> | 常用于跨站识别 |
| 行为与设备信息 | <span className="nscha-yes">不采集</span> | 可能用于风险评分 |
| 求解器来源 | <span className="nscha-yes">本站静态资源</span> | 外部 CDN |
| 服务端留存 | <span className="nscha-yes">短时的一次性记录</span> | 由服务方决定 |
| 交互成本 | 等待一次后台计算 | 可能需要辨认图像 |
| 网络可达性要求 | 只需本站可达 | 需第三方域名可达 |

<p className="nscha-note">右列为通用类别描述，不代表任何具体产品的实现。</p>

## 换了什么、没换什么

**换掉的**是「通过了解访客来判断风险」这条路径：我们改用「每题都要算」这种与身份无关的信号。

**没换的**是验证的目的：仍然要让批量提交变贵，仍然要在服务端校验答案，仍然要与其他限流手段配合。

## 取舍

托管式方案通常具备跨站风险情报与更成熟的对抗经验；NSCHA 换来的是**数据不出站**、**无第三方可用性依赖**，代价是放弃这些情报，并把难度调优的责任留在自己手里。

:::tip

如果你的业务已经依赖跨站风险评分，NSCHA 更适合作为「不采集数据」场景下的替代，而不是叠加使用。

:::
