# 索取挑战

浏览器向 `POST /api/auth/captcha/challenge` 请求一份挑战。这一步**不写数据库**。

## 响应结构

```json
{
  "challenge": {"c": 20, "s": 32, "d": 3},
  "token": "<签名的挑战串>",
  "expires": 600
}
```

| 字段 | 含义 |
| --- | --- |
| `c` | 子挑战数量（默认 20） |
| `s` | 每个子挑战的盐长度（默认 32 字节） |
| `d` | 目标哈希的前导零个数（默认 3） |
| `token` | 带签名的挑战令牌，内含参数、用途与过期时间 |
| `expires` | 挑战有效期（秒） |

## 为什么可以不落库

参数全部写进 `token` 并用 `CAP_SECRET` 签名。服务端稍后收到兑换请求时，先验签，再从令牌里读回 `c / s / d / scope / exp` 自行验算 —— 不需要在签发时先存一份记录。

这带来两个直接好处：

- 挑战接口是纯计算，不产生数据库写入
- 用户刷新页面、切换标签页，不会留下「悬挂」的服务端状态

:::caution

**服务端不要自己复现求解** — 每个子挑战的盐由客户端按「挑战令牌 + 序号」派生。服务端无法也不应重建这个派生过程；它的职责是验证客户端交回来的答案，不是替客户端把题算一遍。

:::

## 签名密钥

`CAP_SECRET` 必须足够长且随机。它同时保护挑战参数不被篡改 —— 否则攻击者可以把 `d` 改成 0，给自己发一道免费题。轮换密钥会让所有在途挑战立即失效，应安排在低峰期。
